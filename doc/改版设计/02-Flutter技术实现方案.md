## 1. 技术决策

| 项目 | 选择 | 理由 |
| --- | --- | --- |
| 客户端 | 继续 Flutter / Dart，支持现有 iOS / Android | 保留当前工程、页面资产和分享能力 |
| 状态管理 | 沿用 Riverpod；本次不同时做大版本升级 | 降低功能改版与基础库迁移叠加风险 |
| 计算 | 无 Flutter 依赖的纯 Dart 领域模块 | 可独立校验、复用到不同页面、为以后移植保留契约 |
| 规则 | 包内版本化 JSON 数据 + 政策摘要 | 离线可用、来源可追溯；首发没有后台依赖 |
| 方案与草稿 | SQLite，经 `sqflite` 仓储封装 | 原子保存、迁移回滚、按方案检索、持久化完整快照 |
| 展示偏好 | SharedPreferences | 只保存非关键的显示偏好，不再承载全部历史 |
| 路由 | 先沿用 Navigator，增加三栏壳与明确路由参数 | 当前不需要为深链额外引入路由框架 |
| 分享 | 复用现有 screenshot / share_plus / gal，经服务接口调用 | 沿用平台适配，重做版式与长图分段 |
| 网络与账号 | 首发不新增 | 收入与方案不上传；只在用户打开政策链接时使用浏览器 |

分层原则参考 [Flutter 架构指南](https://docs.flutter.dev/app-architecture/guide)，具体模块划分是本项目设计。SQLite 方案参考 [Flutter 持久化指南](https://docs.flutter.dev/cookbook/persistence/sqlite)；SharedPreferences 官方说明其写入返回并不保证数据已落盘，因此不适合承载关键数据。[插件说明](https://pub.dev/packages/shared_preferences)

新增依赖预计仅 `sqflite`、`path`，UUID/摘要可选用维护良好的小型库。依赖兼容性和具体版本在开发时针对现有 Flutter/Dart 与锁文件确认；本轮不升级或安装依赖。

## 4. 数据模型契约

### 4.1 版本分别管理

建议：`inputSchemaVersion = 4`、`snapshotSchemaVersion = 3`、`resultSchemaVersion = 1`、`rulesSchemaVersion = 1`；另有 `engineVersion` 和具体 `ruleBundleId`。数据库版本独立维护。

结构版本决定怎样解析数据；引擎版本说明使用哪套算法；规则版本说明使用哪份参数。三个概念不能混成一个字符串。V2 数据放入新的数据库，不让旧版解析器误读。

### 4.2 ScenarioInput（提交后不可变）

| 字段组 | 必需内容与约束 |
| --- | --- |
| 身份与期间 | scenarioId、taxYear、residentType、employmentType；P0 固定居民/普通在职/全年同一单位 |
| 城市与模式 | cityId、cityCode、jurisdictionId、policyMode（verified/custom/legacy）、医保档次/工伤行业；稳定 ID 与行政区代码分开，不能用展示名作主键 |
| 工资 | grossMonthlySalaryCents，工资输入是税前现金工资 |
| 奖金 | amountCents、paymentMonth、mode（separate/merged/compare）、eligibilityConfirmed、alreadyUsedSeparately |
| 社保基数 | source（known/currentSalaryEstimate）、referenceBaseCents，必要时按险种覆盖 |
| 公积金基数 | source（known/currentSalaryEstimate/followSocialReference）、referenceBaseCents |
| 缴费覆盖 | 每险种个人/单位比例、实际基数、固定费用、启用状态、自定义边界；记录默认值、覆盖来源、作用月份及城市/人员/档次作用域 |
| 税务确认 | 自定义模式可扣除缴费额、需计入工资应税收入的单位超标准福利额；未知时状态为 needsConfirmation |
| 扣除 | 每月专项附加扣除合计；基本减除费用由规则给出，不让用户重复填写 |
| 个人养老金 | contributionSchedule（每月等额/一次）、amountCents、month、deductionTiming（withholding/annualSettlement） |
| 明示假设 | 固定月薪、规则归属月口径、本人转入养老金账户、是否采用未来月份预测规则 |

UI 中“compare”在应用层展开成两个确定输入；每个引擎调用只有 separate 或 merged。快照保存比较结果时记录两套确定结果和用户当前选中的结果。

### 4.3 月度标准化输入

由 ScenarioInput 展开出按 1–12 月排序的 MonthInput：工资、当月奖金、所用规则 ID、各项实际基数与费率、实际缴费、允许扣除额、专项附加扣除、个人养老金缴费和本期允许扣除额。P0 工资不变，政策和奖金/养老金所在月份可变。

即使 UI 只有固定月薪，计算层也必须逐月解析政策。该结构为奖金与年中规则变化服务；不能据此宣称已支持入离职、多单位或任意调薪。

### 4.4 RuleBundle 与 ContributionRule

| 字段 | 用途 |
| --- | --- |
| id / schemaVersion / taxYear / cityCode / employmentType | 唯一识别及适用人群 |
| effectiveFrom / effectiveTo | 实际生效区间；不以发布日期代替生效日期 |
| publishedAt / verifiedAt / reviewDueAt | 发布、核验、复核时间 |
| sources[] | 官方标题、URL、发布机构、文件号、相关条款说明 |
| reviewStatus | draft / verified / incomplete / superseded；不是单靠时间戳判定有效 |
| taxBrackets / bonusBrackets | 两张独立税表、适用截止日期、基本减除费用、养老金年度限额 |
| contributionItems[] | 每险种独立上下限、基数来源、个人/单位比例和固定金额、计费规则 |
| taxTreatment | 哪些个人缴费可扣除、限额计算、单位超标准部分处理；未知不是零 |
| roundingPolicy | 舍入单位、方式、先后顺序；地区缴存整元规则可配置 |
| bundledWith / applicability | 医疗包含生育等合并关系，禁止重复计费 |

全局“一个社保基数 + 所有险种同一限额”只可作为输入便利，不能成为城市规则的数据假设。单位行业差别工伤费率需明确单位适用值或标为估算。

公积金的合法可选范围、产品预选值、用户实际比例分开建模。来源和有效期需要能绑定到具体字段；仅核验基数不能把同条候选费率标成 verified。采集格式 `collection-1` 不可直接作为生产规则加载；完整字段、状态与本轮候选数据见[全国城市配置方案](04-全国城市配置与自动带入方案.md)。

### 4.5 CalculationResult 与 Trace

结果包含：输入快照、12 个 MonthResult、AnnualSummary、规则完整性、明确假设、引擎版本、所有用到的规则与覆盖值。

MonthResult 保存收入、个人/单位逐项缴费、实际扣款与可扣除额、累计税基各组成、税档、累计应纳税额、本期工资税、单独奖金税、到账、养老金后可用现金、企业成本。金额型字段按语义分为非负输入、有符号累计余额/现金/差额，不能再用一个“所有字段非负”的解析器。

AnnualSummary 分别保存：工资、奖金、个人缴费、单位缴费、养老金投入、工资预扣、奖金单独税、综合所得年度应纳税估算、汇算差额、全年到账、可用现金、公积金、基本养老个人缴费、企业成本。年度税基来自全年累计账本，不再使用旧版 `taxableIncomeIncrementCents` 简单求和。

CalculationTrace 是有类型的步骤数据：步骤 ID、操作数、结果、来源规则、说明键。不存只有文字的公式。UI、月份详情和分享从同一轨迹格式化，防止截图中出现的“数值正确、解释公式错误”。

### 4.6 ComparisonViewModel 与指标字典

根据实际对比截图新增独立对比展示契约。输入是两个已保存快照 ID、各自选中的奖金策略、所选自然月份（默认 1）、列顺序和 onlyDifferences。比较不同已选奖金策略属于不同方案条件，须展示差异；此用例不替代“同一方案两种奖金策略”的计算用例。

| 数据 | 必需内容 |
| --- | --- |
| ComparisonHeader | 两份方案的 ID、名称、城市、纳税年度、保存时间、规则版本、已选奖金策略 |
| ComparisonMetricDefinition | 稳定 metricId、分区、标签、期间 annual/monthly、缴费方 employee/employer/bilateral/none、口径 basis、单位、值类型及显示顺序 |
| ComparisonCell | value（整数分/基点/文本/枚举）、availability（known/missing/notApplicable）、数据来源字段路径、规则 ID；已知 0 与缺失分开 |
| ComparisonRow | 指标定义、A/B 单元格、是否可比及原因、difference、可选百分比、关联明细行 |
| ComparisonViewModel | 年度汇总、所选月结果、个人/单位缴费明细、输入条件、缺失与口径提示、当前筛选范围 |

指标按稳定 ID 匹配，不按中文名称或数组位置匹配。`annual.housingFund.bilateral` 与 `monthly.housingFund.employee` 是不同指标，不能因都叫“公积金”而共用取值器。个人养老金与基本养老、专项附加扣除与基本减除费用也必须有不同 ID。

| 页面指标 | 数据来源与约束 |
| --- | --- |
| 年度双边公积金 | 快照中全年个人与单位公积金之和；不再乘 12 |
| 指定月个人/单位公积金 | 通过 month 键查对应 MonthResult 的个人/单位字段；不用年度值除 12 |
| 指定月到账与个税 | 对应月的真实预扣后到账和工资税/单独奖金税；不能拿第一条月记录或月均填充其他月份 |
| 个人/单位五险 | 对应方、对应险种的月度组成；合并项目显示包含关系，缺失不视为零 |
| 年度/指定月扣除 | 已保存输入和规范化扣除账本；原始标签不清楚时不猜测其税务类别 |
| 企业成本与差异来源 | 保存的企业成本及组成；可由已知组成展示差异，不能从总差额倒猜某个费率 |

旧快照只在语义可明确映射时生成对应指标；有历史年度成本但没有月明细，不据此推算每月成本。已知字段可作加总推导，但不得新增没有证据的月份、税率或单位缴费信息。

只有期间、币种、口径一致且两侧均有已知值，才计算差额；金额用分相减，费率差用整数 ppm 相减并显示百分点。文本差异不计算数值百分比。A/B 交换后重算差额；筛选以原始值和可比性判断，不比较格式化后的字符串。缺失/不可比项目即使两侧都为空，也保留为“信息不足”。

CompareController 只保存选择状态，通过快照派生展示模型；切换月份不重跑税额计算、不写入历史。年度分区不随月份切换变动。按 metricId + period + month 保持行身份，防止重建时错位。页面和分享使用同一 ComparisonViewModel；其月份、列顺序与差异筛选状态冻结到导出请求。

普通字号使用一个共享纵向滚动容器和固定方案表头，表格各列共同行高。采用按行构建的列表降低长表渲染量；大字体使用同指标 A/B 卡片。没有已证实需求时不引入复杂表格依赖。

## 5. 计算规则与精度

### 5.1 金额和舍入

- 金额采用整数分；新模型费率采用整数 ppm（1,000,000 = 100%，1250 = 0.125%）。旧整数 bps 转为 ppm 时乘 100。输入通过十进制字符串解析，百分数最多四位小数，避免先转 double；不把 0.125% 截为 0.12% 或 0.13%。
- 保留当前上限 99,999,999,999 分；对累计值和乘积也进行边界检查，非法值在领域入口返回字段错误。
- 默认比例缴费采用非负整数四舍五入到分；城市规则需要按元或其他单位舍入时由该项规则明确指定。无法确认舍入口径时，该模板不能标为全部已核验。
- 先按月、按个人/单位每一项缴费舍入，再求和；税额按税额规则舍入；全年汇总求月值，不用年基数重新算缴费。
- 差额相减用有符号整数；展示四舍五入不回写领域金额。精度验收应到分精确，不能普遍放宽到“差一分钱也算对”。

未来移植到 TypeScript 时必须再次验证安全整数范围及所有中间乘积，不直接复制 Dart 的整数安全假设。

### 5.2 缴费解析

1. 为每个月、每项缴费解析唯一有效规则；发现区间重叠或缺失返回 policyCoverageError。
2. 取得该项参考基数；当前月薪仅是估算来源，已知实际基数优先。
3. 标准模式依据该项上下限取得适用基数，并保存调整前/后数值及原因。
4. 对个人与单位分别计算比例项及固定项；不把已合并的生育保险再加一次。
5. 分开生成实际扣款、可税前扣除额、需要加计应税收入的单位福利额。

超出政策标准的自定义公积金或其他缴费不能默认全额税前扣除。P0 对未覆盖的超标税务处理不做推断：允许展示缴费和企业成本，税后测算需用户提供已确认的可扣除额及应税福利额，标识自定义；否则阻断税后结果。

旧版 3 元固定大病统筹只属于旧演示规则，不成为全国默认。其他地区的固定费用及其税前扣除属性必须分别核验。

### 5.3 工资累计预扣

对第 m 月定义：

- Gᵢ：现金工资；Bᵢ：并入综合所得的奖金；Uᵢ：需要计入税基的单位福利等已确认非现金收入。
- Sᵢ：允许税前扣除的个人社保、公积金及其他已确认专项扣除。
- Eᵢ：适用于预扣的专项附加扣除。
- Pᵢ：本月可在预扣环节扣除的个人养老金；汇算扣除模式下为 0。
- D：月基本减除费用，当前已核验规则为 5,000 元；P0 任职月份为 1–12。

累计原始余额 Rₘ = Σ(Gᵢ + Bᵢ + Uᵢ − Sᵢ − Eᵢ − Pᵢ) − D × m。

累计计税基数 Yₘ = max(0, Rₘ)。对 Yₘ 查累计税率表，得到累计应纳税额 Tₘ；本月工资预扣 Wₘ = max(0, Tₘ − Σ此前实际预扣 Wᵢ)。

累计应纳税额 Tₘ = max(0，按分舍入后的 Yₘ × 税率 − 速算扣除数)。P0 不包含额外减免税项目，不能用这个简化入口覆盖具有特殊减免资格的情况。

| 累计税基上限（元） | 税率 | 累计税速算扣除数（元） |
| ---: | ---: | ---: |
| 36,000 | 3% | 0 |
| 144,000 | 10% | 2,520 |
| 300,000 | 20% | 16,920 |
| 420,000 | 25% | 31,920 |
| 660,000 | 30% | 52,920 |
| 960,000 | 35% | 85,920 |
| 无上限 | 45% | 181,920 |

上限归低档。这张表与奖金表分开存储，不因为部分边界数字相同就复用速算扣除数。

**关键：先累计原始收入和扣除，再对累计税基截零。** 不能把每月负余额丢弃后累计；也不能把此前已预扣替换成“上月理论应纳税额”。本期差额为负时不通过工资预扣退税。规则依据[个人所得税扣缴申报管理办法第六条](https://fgk.chinatax.gov.cn/zcfgk/c100012/c5194838/content.html)。

用于工程验收的反例：第 1 月税前工资 4,000，第 2 月 10,000，无任何缴费与附加扣除，均在职；第 2 月累计应税额为 4,000，累计税 120。旧式逐月截零会得到税基 5,000、税 150。该例测试领域能力，不意味着 P0 开放变动工资 UI。

### 5.4 全年一次性奖金

单独计税：使用奖金 B / 12 所在的月度换算税档，然后用**整笔奖金 B × 税率 − 月度速算扣除数**。不要把奖金先分成 12 次纳税，不要使用年度速算扣除数。查档可直接比较 B 与“月度档上限 ×12”，避免在 B /12 上引入浮点舍入。

| 奖金总额上限（元） | 税率 | 奖金速算扣除数（元） |
| ---: | ---: | ---: |
| 36,000 | 3% | 0 |
| 144,000 | 10% | 210 |
| 300,000 | 20% | 1,410 |
| 420,000 | 25% | 2,660 |
| 660,000 | 30% | 4,410 |
| 960,000 | 35% | 7,160 |
| 无上限 | 45% | 15,160 |

档位上限归低档。单独奖金税记入发放月份并从当月到账扣除，但不进入工资累计税基，也不计入工资累计已预扣状态。

并入方式：将整笔奖金加到发放月份 Bᵢ，进入工资累计账本；该模式没有另一个“奖金税”重复扣款。可以另展示相对无奖金方案的增量税，但这只是解释指标，不能再从到账扣一次。

支持截止日期来自[2023 年第 30 号公告](https://www.mof.gov.cn/jrttts/202308/t20230828_3904461.htm)。一年只能使用一次的条件按[税务局奖金问答](https://shanghai.chinatax.gov.cn/zcfw/rdwd/202501/t474844.html)建模。没有资格确认或超过规则有效期时不生成可采用的单独计税结果；普通季度奖不作为本入口。

### 5.5 个人养老金

模型把“实际缴费计划”与“税务扣除计划”分开。P0 允许每月等额缴费或指定月一次缴纳，年度合计不得超过所选规则限额。当前规则限额为 12,000 元/年，凭证与扣除环节依据[2024 年第 21 号公告](https://fgk.chinatax.gov.cn/zcfgk/c102416/c5237110/content.html)。

当年预扣模式：在缴费当月计入可扣除额，明确假设凭证及时交给扣缴单位；每月和累计扣除不能超过已缴费及年度剩余额度。一次性缴费不得自动平均分到过去月份。

汇算模式：本年工资预扣不减养老金；年度应纳税估算扣除合规全年缴费，单列可能退税。无论选哪个扣除环节，个人养老金实际转出只影响“养老金投入后可用现金”，不增加企业成本，也不冒充基本养老缴费。

### 5.6 现金、年度税额与比较

当月到账 = 现金工资 + 现金奖金 − 个人实际强制缴费/固定费用 − 工资预扣 − 单独奖金税。

当月可用现金 = 当月到账 − 本人转入个人养老金金额。

企业成本 = 工资 + 奖金 + 单位各项缴费/固定费用。个人扣款是从工资中代扣的组成，不能再额外加到企业成本。

年度应纳税估算按本工具覆盖的全年综合所得收入及全年允许扣除重新计算；单独奖金税另加。综合所得汇算差额 = 综合所得实际预扣合计 − 综合所得年度应纳税估算。这里不实现免于补税等全部申报办理条件，只展示税额差异，不生成报税结论。

主卡“全年到账（预扣后）”必须等于月度到账求和；不能将预计次年退税加进本年到账。比较奖金策略时用同一全年输入下的总应纳税估算，并同时保留预扣后到账差异，避免扣除时点造成误判。

## 6. 城市政策的数据发布机制

### 6.1 发布粒度

城市目录只含代码、名称、拼音和索引；规则按城市、人员类型、险种、有效期拆分。国家税务规则与地方缴费规则分开。北京社保与公积金从 2026 年 7 月调整，必须能同时加载当年早期和后期规则，不以系统当前月份的一套参数覆盖全年。

全国城市配置是 V2.0 范围。本轮采集底稿有 337 个城市、31 个省级地区；省直管县、兵团等独立统筹区仍须补齐。发布包与采集库分离，候选数据不得通过兜底逻辑进入“已核验”计算。城市、统筹区和行政区版本映射的细节见文档 04。

核验参考：[北京 2026 社保通告](https://rsj.beijing.gov.cn/xxgk/2024zcwj/202608/t20260821_4831461.html)、[北京 2026 公积金通知](https://banshi.beijing.gov.cn/zcjd/202608/t20260831_428685.html)。本轮只确认了部分关键边界，未交付可直接发布的北京完整规则包。

### 6.2 规则包上线门槛

采集官方原文 → 记录金额、比例、人员条件、生效期与舍入 → 复核税前扣除处理 → 校验 12 个月覆盖及区间无重叠 → 用上下限算例核验 → 标为 verified → 随 App 发布。

ruleBundle 使用稳定 ID 和内容摘要；同 ID 内容不得悄悄变化。政策更正创建新版本并说明更正点。当前测算可以采用新版本，已保存快照不被批量重算。

未知未来月份不得自动判为已核验。首发可限制在完整覆盖年度，或让用户明确采用“按现有规则预测后续月份”的自定义假设；后一种结果始终显示预测标记。离线应用只承诺展示已安装版本的规则核验日期，不声称实时获取最新政策。

政策追溯调整按最终生效月分配应缴估算，实际补扣月份还原不在 P0。这样年度应缴与实际某月补扣工资单可能不同，产品结果明确采用“按政策归属月估算”。

### 6.3 规则服务契约

| 操作 | 输入 | 输出/失败 |
| --- | --- | --- |
| 查询城市 | 搜索词 | 城市索引及模板覆盖状态 |
| 解析规则 | 城市、年度、人员类型、用户覆盖 | 12 月完整规则集合，或缺失/冲突项目列表 |
| 校验输入 | 草稿、适用规则 | 已解析输入或字段错误；不偷偷把未知值当 0 |
| 工资测算 | 已解析输入、规则集合 | 稳定结果与轨迹 |
| 奖金比较 | 相同基础输入 | 两种结果、差额、可用性与限制 |
| 方案比较 | 两份快照、已选策略、统一月份、列顺序与筛选 | 年度/月度/缴费/输入分区，指标差额及不可比项目列表 |

不要求首发建设规则后台、在线爬虫或账户 API。规则采集是发布流程，不在用户每次计算时临时联网抓取。

默认值解析单独使用 ContributionDefaultsResolver；规则不可变，用户只编辑方案覆盖。切城市保存原作用域草稿，原子加载新模板，工资/奖金/扣除保留；旧城市比例不延续。单项恢复删除对应覆盖，整体恢复删除当前城市缴费覆盖及自定义边界。公积金预选合法范围上限属于产品策略，写入快照并标为可调整假设；不得伪装成官方唯一费率。

## 7. 存储、快照和旧数据迁移

### 7.1 SQLite 数据结构

| 表 | 主要内容 |
| --- | --- |
| drafts | 草稿 ID、版本、输入 JSON、更新时间；保存有效输入与未提交文本状态时分开存 |
| plans | ID、名称、创建时间、保存时间、城市、年度、engineVersion、snapshotVersion、结果状态、快照 JSON、内容摘要 |
| migration_runs | 源格式版本、迁移批次、状态、数量、错误摘要，不存薪资到日志 |
| legacy_payloads | 旧记录原文、来源键/索引、处理状态、对应计划 ID；仅本机恢复用途 |

P0 的完整快照 JSON 内保存输入、结果、当时所用规则参数与来源；查询常用的名称/时间/城市/年度另建列及索引。无需把每个计算步骤都拆成单独关系表。比较读取两份快照即可。

命名属于可变元数据；金额、输入、规则、计算轨迹不可原地更新。复制重算创建新 ID，保存 `derivedFromPlanId`。ID 使用随机唯一标识，不再依赖时间戳加进程内序列。

保存结果通过单次数据库事务写入，事务提交后才显示成功。写入队列串行处理保存/删除/清空，并使用 operationId 或内容指纹避免连点重复。事务失败保留页面结果，不回写不一致的列表。[sqflite 事务文档](https://pub.dev/packages/sqflite)

### 7.2 当前数据入口

- 设置键：`salary_calculator.inputs.v1`，内部 schema 1/2/3。
- 历史键：`salary_calculator.history.v1`，每条 schema 1/2，嵌套 CalculatorInputs。
- schema 2 通常有完整 12 月快照；schema 1 可能只有年度摘要。

键名中的 v1 不等于内层结构版本。必须逐条识别，不按键名猜测。

### 7.3 迁移步骤

1. 启动迁移前读出旧原始字符串；不先调用会静默跳过坏记录的旧仓储。
2. 在新库记录迁移开始，逐条校验；有效、损坏、未知版本分别统计。
3. 将设置映射为 legacy 自定义草稿：保持工资、扣除、基数模式、固定费率和 3 元示例费；城市与年度未知，不填“北京 2026”。
4. schema 2 原样保存原年度和月度金额；必要时验证其合计，发现不一致保留原文并标“旧记录数据不一致”。
5. schema 1 没有明细则显示原年度摘要，“原记录未保存月明细”。不得用新引擎补出貌似原始数据。如未来确需重建，仅在对应旧引擎版本可确认、重建年度与原摘要吻合时显示“按旧规则重建”。
6. 通过源记录稳定标识/摘要保证重复启动幂等；每条映射及进度在事务内提交。损坏记录入隔离区，不能导致整个应用不可用。
7. 核对迁移数量、金额摘要与回读结果后标记完成；保留旧原文到迁移稳定期，后续由数据管理统一清理。
8. 迁移失败时回滚新事务，旧键不变；可重试或只读查看旧结果，不以空列表覆盖旧数据。

清空本地数据操作须同时处理新库、迁移备份、旧键和迁移状态，保留“用户已清空”的有效状态，防止下次启动重新导入已经删除的旧方案。

### 7.4 回退策略

开发和灰度阶段保留旧数据、旧只读展示及迁移开关。新库写入不双向覆盖旧格式。回退旧 App 只能看到升级前的旧记录，V2 新方案仍保留在新库但旧 App 无法显示；不能承诺降级版本完整可读。

SQLite 默认不是加密数据库，首发不宣传加密存储；存于应用私有目录、避免日志泄露。系统备份与删除范围在隐私说明中按实际平台配置说明。

## 8. 状态、交互与渲染实现

启动初始化优先读取持久化草稿或旧版迁移结果；仅确认首次无数据，或用户主动新建空白方案时，采用产品默认城市北京、普通企业职工、当前年度，通过 PolicyResolver 与 ContributionDefaultsResolver 自动加载缴费参数。工资为空时仅带入范围、费率和基数模式，实际基数等待工资输入。默认城市属于产品配置，不在页面硬编码一套北京费率；规则按所选月份解析并保留真实核验状态。存储读取失败不得当成首次安装，原草稿和历史不得被默认值覆盖。再次启动恢复原城市及覆盖；复制方案继承源输入；恢复城市默认操作不修改 cityId。

DraftController 管理原始文本、解析值、字段错误、是否修改和持久化状态；CalculationController 管理 submittedInput、result、requestId；PlanRepository 管理已保存快照；CompareController 管理两个快照 ID、已选策略、所选月份、列顺序、差异筛选与展开项，派生第 4.6 节的比较展示模型。

计算状态：empty → editing → valid → calculating → calculated。保存状态独立为 idle / saving / saved / failed，避免“计算成功”被当成“保存成功”。

P0 计算量仅 12 月 × 少量策略，先同步纯函数执行；只有基准测量证明阻塞界面时才引入 isolate。不为简单计算提前建设并发任务系统。

用户快速切换城市/年度时按 requestId 丢弃过期的规则加载响应。点击计算后冻结输入和规则；返回编辑不改变已展示的旧结果。复制历史不触发原快照重算。

三栏各自保留滚动与选择状态。详情路由传 planId 或不可变结果 ID，不能只传“读取当前全局计算结果”。分享服务也使用该 ID 对应的快照。

## 9. 结果图与政策说明

分享服务只接收 ShareViewModel，来源是 CalculationResult 或 Snapshot；不在绘图期间重新计算。统一货币格式、字段标题、口径与年度合计。长图预估尺寸，超限按年度摘要/月度明细拆图，释放渲染资源，处理取消/无权限/失败。

政策与算法说明继续使用本地 Markdown，但将“当前使用的参数、来源日期、有效期”动态链接到结果中的规则 ID；禁止说明页显示最新版规则、历史详情却未标旧版。

## 10. 测试策略及交付约束

必须先通过独立计算基准，再接页面。算法采用纯 Dart 测试；Widget 测试关注草稿提交、异常和不同来源的结果；迁移测试采用真实结构的脱敏样本；真机验证存储、分享与长图。

关键断言：

- 逐月到账求和等于主卡年度到账；各缴费明细合计等于摘要。
- 工资预扣与奖金单独税隔离；单独模式不改变工资累计账本。
- 个人养老金既不成为企业成本，也不重复扣现金；年度限额不超扣。
- 修改单位独立费率只影响单位对应缴费/成本；如规则存在应税福利关系，则按该关系显式影响税基。
- 规则覆盖完整且唯一；缺失数据不降为 0。
- 保存与回读结果逐字段一致；旧快照不因规则升级改变。
- 迁移中断、损坏单条、重复运行、清空后重启全部有确定结果。

完整样例和阶段门槛见[验收与实施计划](03-参考分析验收与实施计划.md)。本轮只制定这些测试，不宣称已运行 Flutter 单测或真机验证。
