# 全国城市配置与自动带入方案

版本：0.4 评审稿 · 2026-11-09 · 默认带入北京参数 · 数据采集基准仍为 2026-11-06

## 1. 已确定的产品要求

用户已明确要求：先收集全国各城市默认配置；选择城市后自动带入社保、公积金基数范围及个人、单位缴费比例；这些参数允许手动修改。本项属于 V2.0 核心范围，替代此前“北京先发、其他城市后续扩展”的建议。本轮交付配置采集底稿、交互设计与技术约定，尚不修改 App 业务代码。

首期人员范围仍为中国大陆普通企业在职职工。全国覆盖是产品目标；城市条目、候选参数、经核验可发布规则是三个不同的完成度，不能把目录数量当成生产可用数量。

2026-11-09 用户确认：**默认带入北京参数。** 首次安装自动选北京，并带入所选年度适用的社保、公积金基数范围和个人/单位比例；无需用户先选城市，仍可切换地区或手动调整。已有草稿优先恢复，不因启动再次覆盖成北京。

### 2.1 全国范围还需补齐的层级

- 省直管县级行政单位、兵团师市、区县差别政策，不能机械并入邻近地级市。
- 同城的省直公积金中心、行业缴存中心、独立园区等，只有确认存在不同政策时新增统筹区配置。
- 需要分档的医疗保险、工伤行业类别和单位浮动费率，不能只用城市名称确定。
- 历史有效区间、暂停或阶段性优惠、补充公积金等需要单独采集。

这 337 条是当前数据覆盖范围，不能声称覆盖了全国所有独立缴费主体。港澳台采用不同制度，不纳入本轮大陆薪资计算器规则；省直管县、兵团等大陆覆盖缺口仍属于全国采集待办，不从目标中删除。

## 4. 用户看到的交互

### 4.1 城市选择与自动带入

1. 首次进入首页默认选择北京并触发参数加载；用户可主动切换城市。必要时进一步选择统筹区、医保档次等会实质影响结果的选项。适用信息不明确时，只询问该城市需要的项目。
2. 从本地规则包按城市、人员类型、所选年度解析逐月默认值，一次性填入基数边界、个人/单位费率、固定费用和合并关系。
3. 首页显示“已带入上海参数”，同步更新缴费摘要；年度中途调整显示“按月份应用”。月薪、奖金、扣除不因切换城市改变。
4. 待核验或缺失项直接显示具体缺口，可进入自定义估算。未核验候选只展示为参考；不能静默当成已核验模板。

普通切换不增加确认弹窗。先保存原城市编辑草稿，再加载新城市默认值；原城市手动费率不能延续到新城市。提供“撤销切换”。再次回到旧城市时仍加载默认值，并提供“恢复该城市上次调整”入口；只有用户主动恢复才应用旧覆盖值。

城市选择页状态统一为“已核验”“部分待补”“待核验”“暂无参数”，并展示所选年度的覆盖情况。目录中不出现“能搜索到就默认已支持”的含义。

初始北京默认作用于首次安装及主动新建空白方案；再次启动恢复上次草稿，复制方案保留原城市与输入。工资未填写时不填入示例工资或把实际基数显示成 0，只加载范围、费率和基数模式。北京规则存在缺口时如实展示，默认选中不等于已核验。“恢复本城市默认”恢复当前城市，不自动切回北京。

### 4.3 默认比例的含义

| 参数类型 | 自动带入策略 | 用户修改 |
| --- | --- | --- |
| 有唯一适用值的个人/单位费率 | 按当前已核验规则填入 | 修改后标为自定义 |
| 基本公积金比例 | **产品预选该城市标准范围上限**，双方分别存储；显示“预选，按单位实际调整” | 在当地合法范围内选档；范围外进入自定义，不自动认定全额可税前扣除 |
| 工伤行业与浮动比例 | 优先用户已知实际比例；未知时可预选已核验的低风险行业档并明确“估算” | 选择行业或输入实际比例；不声称全城统一 |
| 医保档次 | 展示有效档次，首次需要时由用户确认；不得跨城市保留 | 切档同步该档费率、基数、费用 |
| 缴费基数 | 默认“用当前月薪估算”，按每项独立上下限核定 | 可填实际核定基数；不改变官方边界 |
| 特殊附加费 | 只有适用条件、资金来源与扣除方式明确才启用 | 金额可覆盖；未知项目不能默认 0 后显示完整结果 |

“预选上限”是本方案的产品默认策略，不是官方规定所有企业都按上限缴费。北京预选 12%、上海预选 7%；各自范围来自已核验文件。其他城市在对应范围完成核验后采用同样策略；候选集里保留上游上限作为待核验预选候选。

### 4.4 手动调整和恢复

- 每个字段保留 `默认值 / 当前值 / 是否覆盖 / 覆盖作用月份`。普通修改默认作用于所选年度全部月份；提交前显示受影响月份。不同月份合法范围不同，逐月验证。
- 用户输入同一个社保参考基数时，各险种仍按各自边界计算；高级模式支持逐险种实际基数。
- 官方基数范围只读展示；用户确需修改上下限时，在高级页建立自定义边界覆盖，并显示原边界。该操作不修改共享城市模板，也不自动改变税前扣除标准。
- 单项“恢复”只清除此字段覆盖；“恢复本城市默认”清除该城市本方案所有缴费覆盖及自定义边界，恢复预选比例、基数模式和默认附加项，不清空工资、奖金、扣除。
- 取消编辑不提交；保存设置后首页摘要和待计算状态更新；已有结果提示重新计算，保存的历史快照保持原样。
- 城市/年度/人员类型/医保档次变化可能影响适用性，默认覆盖值必须有明确作用域，不能只按字段名复用。

## 5. 配置数据与计算模型

### 5.1 三层数据分离

1. **城市目录**：稳定 cityId、官方行政区代码（另维护版本）、省市名称、拼音、别名、统筹区。当前候选集只有上游稳定 key；官方代码尚未映射，显式为空，不能伪造行政区代码。
2. **政策规则包**：按城市、统筹区、人员类型、险种、有效期保存官方边界、可选费率、条件、税务处理与证据。发布后不可原地改写。
3. **方案覆盖值**：用户实际基数、比例、固定金额、自定义边界、作用月份。保存到草稿与方案，不回写政策数据。

解析顺序：城市适用规则 → 已确认的档次/行业 → 产品预选策略 → 当前作用域的用户覆盖 → 逐月合法性与税务校验 → 计算。任何未知条件都不以 0 隐式替代。

### 5.2 生产规则必要字段

| 分组 | 字段与约束 |
| --- | --- |
| 身份 | cityId、administrativeCode、jurisdictionId、employmentType、medicalTier、industryClass；人群条件有类型定义 |
| 时间 | effectiveFrom、effectiveTo、publishedAt、verifiedAt、reviewDueAt；按字段或完整同生效期规则段拆分 |
| 基数 | baseMinCents、baseMaxCents、baseReferenceType；养老、医疗、失业、工伤、生育、公积金分别存储 |
| 比例 | employeeRatePpm、employerRatePpm；可选范围或枚举、步长；禁止把范围上限和法定唯一值混为一个字段 |
| 其他费用 | employeeFixedCents、employerFixedCents、periodicity、fundingSource、cashImpact、taxTreatment |
| 合并关系 | includedIn、enabled、notApplicable；含医疗的生育不重复算，未提供与不适用分开 |
| 默认策略 | defaultSelection、defaultReason、needsUserChoice；产品策略也需要版本记录 |
| 来源质量 | sourceIds、fieldEvidenceIds、status、verifiedFields、missingFields、conflicts |
| 舍入与税务 | 舍入单位/方式/次序、个人可扣除额、单位超额福利处理；不能只存缴费比例 |

费率统一采用整数 `ppm`：1,000,000 = 100%，1250 = 0.125%，金额用整数分。旧模型整数基点不足以无损表示 0.125% 等采集值；旧 bps → ppm 乘 100，显示支持最多四位百分数小数，城市档位优先约束。

采集到的长护险值只用于验证模型表达能力，**不据此默认增加现金扣款或企业成本**。例如深圳官方曾发布征求意见稿，涉及医保基金划转，征求意见文件不能作为已生效规则：[深圳官方信息](https://www.sz.gov.cn/cn/xxgk/zfxxgj/zwdt/content/post_12764418.html)。是否额外支付、是否从个人账户划转必须分别确认。

### 5.3 当前候选 JSON 的使用约束

`schemaVersion = collection-1`，不是生产 `rulesSchemaVersion`。顶层含来源提交、原文件 SHA-256、统计、覆盖缺口和 `fieldEvidence`；城市行保留 `upstreamKey`、年度原标签、质量问题、六类 `items`、医保档次和额外候选字段。

- `null` 表示未知；工伤原始 0–0 基数转换为 null，原文件另行保留。
- `employeeRatePpm / employerRatePpm` 仅录入原始来源实际提供的值；缺失的个人生育/工伤比例不擅自填 0。
- 公积金上限记录为 `rateMaxCandidatePpm`，产品候选预选另存 `productDefaultCandidatePpm`，不填进政策唯一费率字段。
- `fieldEvidenceIds` 只确认记录里列出的字段；基数有效期另以 `boundsEffectiveFrom/To` 标识，不能传播到尚未核验的费率上。
- `upstreamSourceReferences` 是待复核来源清单，URL 的存在、域名或上游状态都不能单独证明数值正确。
- `upstreamNote` 保留原始说明；原数据里推导值、历史值、其他人群口径仍然属于候选内容。

## 6. Flutter 实现约定

| 组件 | 责任 |
| --- | --- |
| CityCatalogRepository | 离线目录检索、别名、城市与统筹区关系、覆盖状态 |
| CityPolicyRepository | 按城市和有效期读不可变规则包，缓存按包版本隔离 |
| PolicyResolver | 解析 12 个月、检查缺口和冲突；返回逐项值与来源，不静默降级到其他城市 |
| ContributionDefaultsResolver | 根据档次和产品默认策略计算可编辑初值，不访问工资结果 |
| ContributionDraftController | 管理默认值、覆盖值和未提交文本；城市切换保存旧草稿、清理作用域、应用新模板 |
| PayrollEngine | 只接受已解析且通过校验的月度输入；保留原有纯 Dart 分层方案 |

仍沿用 Riverpod。界面切换应一次提交完整配置状态，加载过程中禁止以半新半旧参数计算；快速连续切换用 requestId 丢弃过期响应，失败保留原城市和原草稿，不残留新城市标题配旧参数。

草稿作用域至少含 scenarioId、cityId、jurisdictionId、employmentType、taxYear、档次和 ruleBundleId。覆盖值还含 fieldPath、value、months、origin、updatedAt。相同作用域的编辑可恢复，但城市切换默认采用新模板。快照冻结实际用到的政策、用户覆盖、默认策略版本和逐月计算结果。

首发先使用随 App 发布的已核验离线规则包。全国规则后续频繁更新时，可另实现静态 HTTPS 数据包更新：版本清单、摘要校验、完整性校验、原子替换、上一版回退；不需要账号，也不上传工资。此更新能力单独估时，不能把全国初始采集当成持续维护已完成。

## 7. 全国采集和发布流程

1. 建立覆盖清单：以当前 337 条为底稿，补官方代码、特殊统筹区和省直管区域；记录不适用与缺口。
2. 逐省采集共用养老等规则，再逐市采集医保、公积金、失业、工伤及附加项；省级规则可引用，城市适用性必须有依据。
3. 把每个数值绑定官方原文、适用人群与生效日期；分别记录唯一比例、可选比例和企业实际值。冲突并列保留后核定，不能“最后抓到的网页覆盖前值”。
4. 对照官方确认历史分段、舍入、合并关系、费用资金来源与税前处理。原链接失效保留采集元数据，后续补官方替代来源。
5. 运行完整性与算例验收，满足所选期间和全部必需条件后才生成生产规则；候选 JSON 不被 Flutter 资产加载器接受。
6. 发布不可变版本。按官方公告触发更新，在常见调基节点前集中复核；无法核实时保留上次已确认记录与日期，不写成“实时最新”。

全国数据核验是一条独立工作流。当前只完成采集底稿和少量官方字段核验，不给“全国全部核验 3–5 天”这样的无依据承诺。先按一个省实测每城核验耗时、共用规则复用率和来源缺失率，再估算剩余工作量。App 开发可在设计确定后用明确标注的样例并行推进，正式全国默认配置以数据验收为发布依赖。
